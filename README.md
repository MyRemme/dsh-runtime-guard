# DSH Runtime Guard

面向 DeepSeek Harness（DSH）的运行时护栏插件（原 **DSH Flash Stabilizer** 合并升级版，将 **防空转 / 卡死恢复** 与 **操作安全防护** 合为一体）。

- **防空转 / 停滞提示**：监控模型推理、正文和工具结果（工具结果对比前会归一化时间戳、UUID 与耗时噪声），在发现持续重复时提示用户；对话卡顿超过 30 秒时显示「等待输出 · 尚不能判断」观察提示（不自动取消请求）；对通过兼容验证的宿主可启用防护停止（`guard`，可选同时拦截正文重复 `guardStopText`）或有限纠正（`assist`）。检测规则默认覆盖所有渠道和模型（包括第三方自定义模型名）。
- **操作安全防护**：遵守每个对话选择的权限模式；默认关闭，可在面板独立开启。仅查看允许常规读取、拒绝明确修改与敏感驱动器/环境变量直读；仅工作区修改允许普通项目开发，对内联脚本执行（`node -e` / `python -c` / `bun -e`）、越界与危险操作请求 **DSH 原生单次审批**；完全权限默认不追加插件拦截，也可独立开启「完全权限下仍拒绝系统提权」。

## 安装与使用

从 [GitHub Releases](https://github.com/MyRemme/dsh-runtime-guard/releases) 下载适配当前 DSH 的 `.tgz`，或按下文从源码打包。选择实际使用的 profile，并替换下面的安装包路径：

```powershell
dsh plugin --profile desktop add './dsh-runtime-guard-x.y.z.tgz'
```

如之前安装过旧插件 `dsh-flash-stabilizer`，建议先卸载旧包再安装本包；原有 `.flash-stabilizer/` 下的模式、模型范围与操作防护配置会在首次读取时自动兼容并写回迁移至 `.runtime-guard/`。

打开 DSH 的「运行时护栏」面板。主页面直接填满宿主内容区，使用顶部导航切换「实时监控」「操作防护」「监控设置」「插件更新」，不再额外增加侧栏或固定宽高的内部窗口。统计项横向排列，正文和列表使用可用宽度。宽面板并排显示对话与检测记录；窄面板切换列表，记录在固定区域内滚动，不会随数量撑长页面。对话可搜索、展开详情、暂停监控或打开原对话；检测依据折叠显示。对话输入框旁的护栏状态使用宿主原生 `MenuSurface` 弹出卡片并在内部独立滚动，支持 Escape 与点击外部关闭。插件配置页中的内嵌面板单独限制高度，避免撑长宿主设置页。页面切换与选中状态使用短过渡，并遵循系统的减少动画设置。

默认启用监控并只告警。处理模式（`observe` / `guard` / `assist`）及模型范围在「监控设置」中调整；需要缩小范围时，选择「仅选中的模型」，按渠道勾选模型并保存。设置保存在当前 profile，重启后恢复。

在「运行时护栏 → 监控设置 → 磁盘日志与历史记录」打开 **启用磁盘日志**，无需重启即可开始自动保存，开关状态也会保留。页面显示保存目录和写入状态。默认目录为当前 profile 下的 `.runtime-guard/logs/`；已有 `config.logDir` 继续有效。未开启时，新记录只在内存中，旧版从未写盘的记录无法恢复。

日志包含最近 100 条检测事件、最近 `maxSessions` 个对话摘要（默认 128，包括没有告警的对话）、累计监控计数，以及操作防护的脱敏计数与最近 100 条防护事件（`safety-history.json`）。重启时自动恢复为历史记录，新请求到来后继续累计；不会恢复为正在运行的请求，也不会重放历史告警弹窗。对话标识使用哈希，本地会话目录仍有对应项时可打开原对话。保存不含正文、推理、命令、工具参数或原始会话 ID。摘要在变化后合并写入并在正常退出时完成保存；异常强制结束可能丢失最后尚未写入的一小段记录。

关闭开关会停止新写入并保留已有文件。检测事件使用两个轮转 JSONL 文件，每个不超过 `maxLogBytes`（默认 2 MiB）；重启恢复使用单独的有界原子快照 `history.json`。旧版 JSONL 会尽量读回完整有效的事件，历史损坏或写入失败会在设置页面显示原因，监控仍继续。

| 模式 | 行为 |
| --- | --- |
| `observe`（默认） | 记录重复并显示告警 |
| `guard` | 确认推理重复后请求宿主停止本轮（开启「防护停止拦截正文重复」后也覆盖正文重复），单独显示宿主的停止确认 |
| `assist` | 当前回合结束后可提交独立的纠正回合，每个用户任务默认最多两次 |

模式可在「运行时护栏」面板的「监控设置」页面实时切换，也可通过 profile 的 `cordis.patch.yml` 中 `id: runtime-guard` 对应的 `config.mode` 设置。插件要求 Node.js 22.18.0 或更新版本。

## 操作防护

在同一面板的「操作防护」页面打开独立开关，或设置 `config.operationSafety: true`。设置按 profile 保存；面板展示是否生效、检查与审批计数，以及最近的阻止原因和审批结果。整个插件被禁用或卸载时，两项功能都会停止。

权限来自宿主当前会话的 `sandboxPolicy.resolve({session})`，每次调用重新读取。模型传入的 `sandbox_permissions` 不会切换用户选择的模式。

| 权限模式 | 直接放行 | 拦截 / 单次审批 |
| --- | --- | --- |
| 仅查看 `read-only` | 已识别的常规读取命令及读取管道、`str_replace_editor view`（包括工作区外读取） | 明确的写入、编辑、删除及系统提权直接拒绝；`env:` / `hkcu:` / `hklm:` 等敏感驱动器读取、用途无法确认的脚本、未知程序和终端操作请求单次审批，宿主只读约束仍有效 |
| 仅工作区修改 `workspace-write` | 工作区内普通写入/编辑、Python/Node 项目脚本、npm 等构建测试与常见 git 操作；常规读取 | 工作区外写入/执行目录、`node -e`/`python -c`/`bun -e` 内联执行、敏感驱动器读取、删除、危险系统修改、未知或动态执行请求单次审批；系统提权直接拒绝 |
| 完全权限 `danger-full-access` | 所有覆盖工具交由宿主执行（如开启「完全权限下仍拒绝系统提权」则继续拦截已识别的提权路径） | 默认不追加拒绝或审批，DSH 原生限制和系统权限仍有效 |

受限模式下，`terminal_send` 指向现存交互终端，插件不能从当前输入推断其目录、解释器或已输入的半条命令，因此每次发送（含空回车）需单次审批；中断控制键直接放行。普通开发脚本通过 `pwsh` / `bash` 执行可按工作区规则放行。仅工作区修改会检查显式路径与符号链接，但无法证明任意脚本的所有副作用，实际文件边界仍由宿主沙盒执行。

使用 `dsh-ops` 标准模式时，原生 `pwsh` / `bash` 可能被该插件替换为 `ops_bash`，调用被替换的工具会被 `dsh-ops` 拒绝，与本插件权限模式无关。`ops_bash` 的 `command` 与工作区内 `script_path`（含不超过 64 KiB 的现存脚本静态提权/破坏性检查）均按上述规则检查。开发命令后拼接未知命令仍需审批。

审批弹窗顶部展示操作原因、工具名称、权限模式与关键命令/路径摘要，下方附带实际工具参数、工作目录与工作区，不采用模型描述代替命令。只有 `allowed-once` 放行；拒绝、取消、服务异常、权限变化或等待期间防护设置变化都会阻止调用。不同调用、并发调用与子调用分别接受检查。诊断仅保留规则与结果，不保存命令正文、路径详情或原始会话 ID；完整调用及审批记录仍由宿主保存。

操作防护已在 DSH **`0.2.1-rc.2` 与 `0.2.2-rc.1`** 完成实测，并放行具备 `tools.guard` 与 `sandboxPolicy.resolve` 能力的 `>=0.2.1-rc.2 <0.2.3-0` 宿主版本。超出该范围、硬拦截接口缺失或权限服务不可用时，面板显示原因；开启防护期间受保护工具会被拒绝，不会自动降为仅观察。防空转兼容性矩阵不代表操作防护兼容性。

当前覆盖 22 个工具：`pwsh`、`bash`、`ops_bash`、`exec_command`、`terminal_open`、`terminal_send`、`write`、`edit`、`apply_patch`、`multi_edit`、`str_replace_editor`、`ops_write_file`、`ops_edit_file`、`ops_replace`、`ops_copy`、`ops_move`、`ops_remove`、`ops_batch`、`run_code`、`delete`、`remove_file`、`delete_file`。这是有明确覆盖范围的保守命令与路径边界检查，不是完整脚本语义分析或操作系统安全边界。未列出的工具、工具体内部直接启动的子进程、恶意宿主插件及配置篡改不在此模块的完整控制范围。请结合宿主沙盒和独立账户权限使用。[验证范围与复现](compatibility/OPERATION_SAFETY.md)

## 框架与实现

后端使用 **TypeScript、Node.js 和 DSH 的 Cordis 插件框架**，通过宿主提供的模型流、Agent 状态和工具结果接口工作。前端使用 **React**，通过 DSH 的界面插槽注册侧栏面板、会话状态和告警，通过宿主已认证的 RPC 读取诊断和保存设置。TypeScript 与 esbuild 生成安装包内的运行代码，Vitest 用于回归测试。

1. **匹配请求**：将模型流绑定到当前会话、回合和步骤，用渠道与完整模型标识应用监控范围。[插件入口](src/index.ts) · [模型选择](src/model-scope.ts)
2. **检测重复**：按内容块维护滚动窗口，跳过代码围栏。正文和推理检查周期重复，推理还检查间歇反复的短句。规则需要多次确认，工具结果的重复单独告警。[流监控](src/monitor.ts) · [检测规则](src/detection.ts) · [工具检测](src/progress.ts)
3. **报告与处理**：通过宿主接口告警、停止或提交后续纠正。诊断记录去标识的会话、计数和处理动作。插件面板也可检查 GitHub 更新，并在宿主空闲时提交已校验的安装包。[处理逻辑](src/recovery.ts) · [React 客户端](client/client.js) · [更新器](src/updater.ts)

## 升级失败排查

更新分为检查版本、下载校验、交给 DSH 安装依赖三个阶段。下载成功不代表安装成功；安装失败后仍显示实际运行的旧版版本号。修复原因后点击「检查更新」再重试。

后续安装包统一使用 `src/updater.ts`，并在包元数据中声明 `runtimeGuardUpdater: 1`。安装前会自动沿用 `node_modules/.modules.yaml` 记录的现有 pnpm 仓库，备份并修正当前 profile 的 `pnpm-workspace.yaml`，保留其他插件、构建批准、设置和历史；安装完成或启动同步后自动清理过期缓存 `.tgz`（保留当前生效版本及 `package.json` 引用包）。安装仍由 DSH 原生管理器执行，不另起一套包管理流程。

已经安装的旧包不会自动获得新代码。`dist/upgrade-helper.mjs` 是独立兼容入口，包含相同的更新器与 YAML 解析器，无需安装 npm 依赖。旧版用户可完全退出 DSH 后运行：

```powershell
node ./upgrade-helper.mjs --profile "$env:USERPROFILE/.dsh/profiles/desktop" --enable
```

重新打开 DSH 后，它会使用统一更新清单、SHA-256 校验与宿主原生安装器，等待所有对话空闲再升级。它不会修改旧版检测或防护代码；新包提供统一协议后兼容入口不再执行升级。若只需修复当前 pnpm 仓库再使用旧版按钮，将 `--enable` 换为 `--repair-only`；用 `--disable` 可移除兼容入口。启用前会备份原 profile patch，设置与历史不会删除。

- `ERR_PNPM_UNEXPECTED_STORE`：DSH 当前 pnpm 仓库与既有依赖的仓库不同。完全退出 DSH，读取当前 profile 的 `node_modules/.modules.yaml` 中的 `storeDir`，将其仓库根目录写入同一 profile 的 `pnpm-workspace.yaml` 的 `storeDir`。例如已有仓库为 `C:\.pnpm-store\v11`，配置为 `storeDir: C:/.pnpm-store`，保留 YAML 中所有其他配置。pnpm 新版本使用 workspace 配置，不能依赖项目 `.npmrc` 生效。
- `ERR_PNPM_GIT_FETCH_FAILED`：DSH 安装时可能解析 profile 内其他已装插件的 Git 依赖。检查该依赖的网络和 Git 代理，再重试安装。

具体错误见 DSH 原生插件页的安装日志。无需先卸载运行时护栏，也不要删除整个 `node_modules` 或插件设置目录来重试。

## 维护与发布（仅限维护者）

- `npm run test:package`（调用 [test-package.mjs](scripts/test-package.mjs)）：重新打包并验证 `.tgz` 在本地缓存的 35 个真实 DSH 宿主版本中均可加载运行，同时刷新兼容矩阵结果；普通用户无需运行。
- `npm run test:upgrades -- <DSH源码根目录> <pnpm.mjs> <目标包.tgz> <旧包.tgz> ...`：在隔离 profile 中先用真实 pnpm 复现仓库冲突，再用统一更新器和 DSH 原生管理器安装，验证校验、设置保留、兼容入口注册与移除。结果包含源包和目标包 SHA-256。发布脚本要求相同目标包通过历史升级矩阵，未通过不能发布。
- [release-github.mjs](scripts/release-github.mjs) 与 [github-credential.mjs](scripts/github-credential.mjs)：**仅限仓库维护者使用**，用于读取发布凭据、创建 GitHub Release 并推送 `updates/stable.json`；插件自身运行与自动更新从不读取发布凭据。
